00

The 30-second answer

If an interviewer asks “what did you build?”, this is the whole thing in six sentences.

Say this

  1. The DUT is a PCIe Transaction Layer. It takes commands from a CPU over an AXI register interface, pulls data out of system memory over a second AXI interface where it is the master, and turns that into TLPs on a Data Link Layer stream — and back.
  2. It is three concurrent FSMs in one module: state_axi (the register file), state_dll (link training → virtual-channel flow control → enumeration → MEM_WR / MEM_RD), and state_axi_mem (DMA write-back of completion data).
  3. The testbench is four UVM agents. AXI master on the CPU side, an AXI slave memory model on the DMA side, and a split DLL agent — a responder that decodes every TLP the DUT sends and decides what completion is owed, plus a driver that sends it back.
  4. The interesting design decision is that the DLL side is not one agent. The TX path is reactive (no sequencer — it answers whatever arrives) and the RX path is sequence-driven. That split is what lets one background sequence service 16 configuration reads without the test knowing they happened.
  5. Bring-up cost ten distinct bugs, documented with symptom, root cause and fix. The best one is a SystemVerilog compilation-unit trap: a static class member existing twice because the file was `included into two compilation units, so the DUT wrote one copy and the sequences read another.
  6. It runs clean and it does not fully pass. Simulation goes end-to-end with zero fatals, but two of three scoreboard checks receive no data because the DUT paths that feed them are stubbed, and the third compares but mismatches. I can name the exact line that causes the third.

Lead with the failure, not the demo

A candidate who says “it all passes” invites the interviewer to go looking. A candidate who opens with “one check compares and fails 255 of 256 bytes, and here is the line I think causes it” has already demonstrated the thing they are actually being assessed on. Section 07 gives you that line.

Descriptor format

DW0 (0x2000) = { length[15:0], flags[2:0], reserved[12:0] }   →  0x0100_E000  (256 bytes)
DW1 (0x2004) = source / destination address                    →  0x8000_0000  (TX)
                                                               →  0x8800_0000  (RX)

The DUT reads them back as a 64-bit pair in S_ENUM_COMPL_IDLE and takes length = txDescr[31:16]. Note the asymmetry worth knowing: the TX descriptor address is where DMA reads from, the RX descriptor address is where completion data lands.

02

Inside the DUT

One module, three always blocks, no handshake between them. Everything they say to each other, they say through shared variables — which is exactly where the interesting questions live.

The main flow, as a state machine

Be ready for this: the FSM coding style is not synthesizable

Three things an experienced interviewer will spot in seconds, so volunteer them first:

  • The state register is event-driven, not clocked. always @(n_state_dll) state_dll <= n_state_dll; triggers on a change of the next-state value, not on a clock edge. In a real design this is always @(posedge clk) state <= n_state;. As written, if two successive states compute the same n_state value the block never fires.
  • Blocking assignments drive outputs inside clocked blocks. tx_valid_o = 1'b1; in an always @(posedge clk) is a race against every sampler on the same edge. It happens to work here because the DLL agents sample on mon_cb with an explicit input skew.
  • There are blocking time controls inside state bodies. Lines 309, 466 and 479 contain a bare @(posedge clk) in the middle of a case arm. That is behavioural-model style; it cannot be synthesized and it makes the FSM's cycle behaviour hard to reason about from the state table alone.

The correct framing is: this DUT is a behavioural reference model of the Transaction Layer, not RTL intended for synthesis. Its job is to give the verification environment something protocol-shaped to talk to. Saying that up front turns a weakness into a scoping decision.

03

The UVM environment

Four agents, one scoreboard, three virtual interfaces published through the resource database. The shape is conventional; the interesting part is what each agent is allowed to do.

The virtual-interface lookup is fragile, and you should say so

Both AXI interfaces are published under the same scope "AXI", with names "PIF" and "MIF". memory.sv and mem_mon correctly use read_by_name("AXI","MIF", …). But axi_drv and axi_mon use read_by_type("AXI", …), which ignores the name and returns whichever entry of that type the database hands back first. It resolves to proc_if today by luck of insertion order, not by design.

The fix is one word per site: change both to read_by_name("AXI","PIF", …). Better still, move the whole thing to uvm_config_db#(virtual axi_intf)::set(null,"uvm_test_top.env.axi_agent_i*","vif",proc_if), which scopes by component path and cannot silently cross-wire. Being able to say why config_db is preferred over resource_db — hierarchy-scoped naming, and it is the documented front end — is worth having ready.

04

End to end, in order

One pass of pcie_wr_rd_test, from the first register write to $finish. This is the narrative to have memorised — almost every follow-up question hangs off one of these twenty steps.

The same thing in words

Phase 1 · Configuration (0 – ~200 ns)

axi_config_seq writes the traffic-class map, BAR0 base (0xEC00_0000) and payload size (256 bytes), reads two registers back to prove the write path works, and finally sets link_control_reg[0]. That last write sets init_link_training in S_REG_WRITE_RESP, which is the trigger that releases state_dll from S_IDLE_DLL. Then axi_dma_descr_load_seq loads one TX descriptor (source 0x8000_0000, 256 bytes) and one RX descriptor (destination 0x8800_0000).

Phase 2 · Link and virtual channels

The two indication sequences drive linkup and all eight dll_vc_up bits. state_dll walks one state per VC, setting a bit of vc_fc_status_reg each time. It is deliberately literal: eight named states rather than a counter, mirroring how the PCIe spec describes per-VC flow-control initialisation as a distinct handshake per channel.

Phase 3 · Enumeration (~200 – 1965 ns)

Sixteen cfg_rd0 TLPs, one per configuration-space DWORD, register 0 through 15. Each is three header DWORDs with no payload. The responder decodes each one, records reg_num from header DW2, and increments rcvd_tlp_count. dll_cpl_seq wakes, randomises a dll_item whose header_c constraint constructs a legal CplD header from the recorded requester ID and tag, and whose post_randomize() selects the right config-space field for that reg_num. The DUT collects it and moves on. Finally one cfg_wr0 writes BAR0 into the endpoint.

This is the part worth showing off. The completion is not a canned vector — it is derived from the request by constraint solving, so if the DUT changes its tag or requester ID the completion follows automatically.

Phase 4 · MEM_WR (posted)

The test waits (#2500, then on the FSM state mirror) until state_dll reaches S_ENUM_COMPL_IDLE, then writes tlp_transfer_config_reg = MEM_WR and pulses dma_configure_reg[0]. The DUT pulls the TX descriptor, issues four 16-beat AXI read bursts against system memory, assembles payload, and drives an MWr TLP. Posted means no completion is expected: the DUT returns straight to dispatch.

Phase 5 · MEM_RD (non-posted)

Same dispatch, different branch. The DUT frames a 3-DW read request asking for 64 DW and parks in S_PROCESS_COMPLETION_TLP. The responder recognises MRd, the completion sequence fires, and dll_rx_drv streams endpoint memory back. The DUT strips three header DWORDs and pushes the rest into cpltlpdataQ; at sixteen entries it is supposed to raise write_to_axi_mem and hand off to state_axi_mem for write-back into system memory.

Phase 6 · Verdict

After a further #10000 the objection drops and report_phase prints three verdicts from the scoreboard's counters.

Why the #2500 is there, and why it is not a hack

The DUT only decodes register writes in S_REG_WRITE_DATA, reachable only from S_IDLE_AXI. During enumeration state_axi does not return to idle, so a write to 0x1010 issued early would block the sequence on awready forever. The delay is a coarse guard; the wait on the state mirror inside axi_mem_wr_cfg_seq is the real synchronisation.

The honest framing: this mirrors real PCIe, where software programs device registers only after enumeration has set up the BARs — but the clean implementation is a status register the CPU can poll, not a backdoor into the DUT's FSM state. Adding a readable “enumeration complete” bit to vc_fc_status_reg and polling it over AXI would remove the backdoor entirely. That is the answer to give when someone asks whether the testbench is peeking.

05

Checking and coverage

The scoreboard does not decide anything. It reduces every payload to bytes, files them into six queues, and runs three parallel compare loops that only count. The verdict lives in report_phase.

Why the compare loops are shaped the way they are

Payload arrives from two places with different natural widths: AXI gives 32-bit beats aligned to a burst, the TLP stream gives 32-bit DWORDs aligned to a packet. Once those two disagree by even one word, a word-granular compare reports total garbage. Splitting into bytes at least lets a byte-level offset be seen in the mismatch pattern rather than hidden.

The honest criticism, and it is the one to raise yourself: this scoreboard has no notion of a transaction. It has no expected model, no tag matching, no ordering rules. It cannot tell you which TLP a mismatched byte belonged to. A production scoreboard for this DUT would key completions by tag, model posted versus non-posted ordering, and compare whole transactions — and it would fail loudly on an empty queue at end of test rather than silently reporting zero.

Bug #9, the one worth telling

This is the best interview story in the project because it is a genuine SystemVerilog language trap, not a typo.

The structural fix, and the answer to give when asked “what should it be?”: put shared types and shared state in a package and import it, rather than `include-ing a class into multiple units. A package is elaborated once and has exactly one instance of each static, regardless of how many units import it. Alternatively, compile with a single compilation unit (vlog -mfcu). The mirror-in-top_tb fix works, but it works by putting the writer and readers in the same accidental scope — a package removes the accident.

And the deeper answer: a testbench should not need to peek at a DUT FSM register at all. The sequence is waiting for “enumeration is complete”, which is a functional condition the DUT could expose in a status register. Reading it over AXI like software would makes the testbench portable to a different implementation of the same specification — which is the point of verification.

07

Open defects, from reading the code

These are findings from a fresh read of the committed source, not from re-running the simulation. Each names a line. Treat them as hypotheses with strong evidence — and as the most valuable thing you can bring to an interview, because they show you can still find bugs in your own work.

A · The endpoint BAR0 is captured from an empty queue

In dll_tx_responder.sv, the payload state does this:

S_TLP_PAYLOAD : begin
  ...
  if ( (fmt == `CFG_WR0 && type_t == 5'b00100) || ... ) begin
    pcie_common::ep_bar0_base_addr = payloadQ.pop_front();   // line 186
  end
  count = count + 1;
  payloadQ.push_back(vif.tx_data_o);                          // line 190
end

The pop_front() happens before the push_back() of the DWORD currently on the bus. payloadQ is never cleared, and no earlier TLP in the run carries a payload — the sixteen cfg_rd0 requests have fmt = 3'b000, so the responder never enters the payload state for them. So at the cfg_wr0 the queue is empty and pop_front() on an empty queue yields zero.

Consequence chain, and this is the part to walk an interviewer through:

  • pcie_common::ep_bar0_base_addr stays 0 instead of becoming 0xEC00_0000.
  • On MEM_WR, the responder writes payload to dll_cfg_rx::mem[addr - ep_bar0_base_addr + count] = mem[0xEC00_0000 + count]. The array is declared bit [31:0] mem [1024:0]. Every write is far out of bounds and is discarded.
  • On MEM_RD, dll_rx_drv streams back mem[addr - ep_bar0_base_addr] — the same out-of-range index. It returns unknown or zero, not the data the DUT just wrote.
  • The loopback compare therefore sees valid TX bytes against garbage RX bytes, which is exactly the reported 1 match, 255 mismatches — one accidental agreement out of 256.

The fix is one line. The cfg_wr0 payload DWORD is the BAR0 value, so read it from the bus directly:

pcie_common::ep_bar0_base_addr = vif.tx_data_o;

This supersedes the “byte-order or off-by-one” theory recorded in sim/errors.md §12. Check it first: it is a single-line change, and if it is right, the only compare that can pass without new RTL should start passing.

B · The payload state captures one DWORD too many

Same state, the exit condition is tested at the top but does not skip the body:

if (count == pcie_common::packet_len) begin
  n_state = S_IDLE_DUMMY;        // decides to leave …
end
// … but execution continues, and this DW is still consumed:
if (rcvd_tlp == MWr) dll_cfg_rx::mem[...] = vif.tx_data_o;
count = count + 1;
payloadQ.push_back(vif.tx_data_o);

For a one-DWORD cfg_wr0 payload this captures two entries. That is precisely the symptom already recorded in sim/errors.md: “cfg_wr0 payloadQ had 2 entries ec000000 instead of 1”. The fix is to guard the body with else, or add a bounds check before consuming.

D · One claim in the repository README overstates the DUT gap

The README says MEM_WR “frames payload from a hardcoded constant” and therefore never reads system memory. Reading the RTL, that is not quite right: S_MEM_WR_READ_ADDR and S_MEM_WR_GET_DATA genuinely issue AXI read bursts and fill payloadA[] from rdata_m. The hardcoded 32'hEC00_0000 passed to frame_mem_wr_tlp() is the TLP target address in header DW2, not the payload. Correct that sentence before an interviewer reads both and asks which one is true.

The read path that genuinely is stubbed is state_axi_mem's S_AXI_MEM_AXI_RD_ADDR / RD_DATA, which are empty.

F · Smaller items

  • A second instance of the compilation-unit trap, still latent. design/pcie_tl.sv:242–245 declares reg [4:0] state and continuously assigns it from pcie_common::state — unit A's copy, which nothing writes. It is harmless only because state is never read. Delete it, or it will mislead the next reader.
  • vc_fc_status_reg resets to 32'hFFFF_FFFF and is then set bit by bit during VC init. A status register that reads “all channels up” while still in reset is backwards; it should reset to zero.
  • The completion header carries bytecount = 0. dll_item's header_c constrains headerQ[1][11:0] == 0, but the DUT's exit condition from S_PROCESS_COMPLETION_TLP is received_bytecount == bytecount, and received_bytecount starts at 4 on the first payload DWORD. The condition can never be true as written, so the DUT leaves that state only by other means. Worth tracing next to finding A.
  • A config write is acknowledged with CplD. Per the specification a configuration write owes a Cpl, not a CplD. This was a deliberate expedient during bring-up (the DUT does not wait on that completion) and is correctly flagged as such in the log — but say it before someone else does.
08

Defending it

The questions that actually get asked, and answers that hold up under a follow-up.

Volunteer these three before you are asked

  1. “The DUT is a behavioural reference model, not synthesizable RTL.” Event-driven state registers, blocking assignments to outputs, time controls inside case arms. Say it as a scoping decision, because it is one: the DUT exists to give the environment something protocol-shaped to verify.
  2. “Two of three checks receive no data, and I can tell you exactly which DUT paths are missing.” An empty compare is not a passing compare, and the report's matches=0 mismatches=0 is the tell. A production scoreboard would fail loudly on an empty queue at end of test.
  3. “The testbench reads a DUT internal FSM register to synchronise, and that is the wrong shape.” Then explain the status-register alternative. This one turns a criticism into evidence that you understand testbench portability.
Why split the DLL into two agents instead of one bidirectional agent?

Because the two directions have opposite control relationships. The TX side is reactive: the DUT decides when a TLP appears, and the testbench's job is to decode it and decide what is owed. That needs no sequencer — a sequencer implies the testbench chooses what happens next, which it does not. The RX side is proactive: the testbench decides when to assert link-up, when to bring virtual channels up, and when to inject a completion. That is exactly what a sequencer is for.

Forcing both into one agent would mean either a sequencer that is never used for half the traffic, or a driver that also has to monitor. The split keeps each component with one reason to change. The cost is that both agents share one virtual interface, which is fine because only one of them drives.

Walk me through what happens between the DUT sending a cfg_rd0 and receiving its completion.

The DUT frames three header DWORDs in frame_cfg_tlp() and drives them one per clock with tx_valid_o high. dll_tx_responder walks its own six-state machine across those beats: DW0 gives fmt and type, DW1 gives the requester ID and tag, DW2 gives the target bus/device/function and the register number. It publishes every one of those fields into pcie_common statics, matches {fmt,type} against CFG_RD0, sets transmit_tlp = CplD and increments rcvd_tlp_count.

dll_cpl_seq is blocked on @(pcie_common::rcvd_tlp_count). That event wakes it; it does a uvm_do_with on a dll_item constrained to CplD. The constraint block header_c then builds a legal completion header out of the values the responder just published — requester ID, tag, traffic class, attributes all copied back. post_randomize() switches on reg_num and fills the payload with the matching field of the endpoint configuration space. dll_rx_drv drives that header plus payload onto rx_data_i, and the DUT collects it.

The point worth making: the completion is generated from the request by the constraint solver. It is not a canned vector, so it tracks changes in the DUT automatically.

Show me posted versus non-posted in your code.

S_TRANSMIT_TLP_POSTED and S_TRANSMIT_TLP_NONPOSTED have almost identical bodies — both drive header[] then payloadA[] and count DWORDs. The difference is the single line at the end. Posted goes straight back to S_ENUM_COMPL_IDLE: a memory write expects nothing back, so the transaction is finished the moment the last DWORD is on the wire. Non-posted goes to S_PROCESS_COMPLETION_TLP and parks there, because a memory read owes a completion and the transaction is not finished until it arrives.

What is missing, and I would flag it: there is no completion timeout. If the link partner never answers, the DUT waits forever — which is exactly the failure mode that made the sim hang during bring-up. Real hardware has a completion timeout timer and reports an uncorrectable error.

Your report prints FAILED with zero matches and zero mismatches. Is that a real failure?

It is a real failure, but not the failure the message implies. Zero of both means the compare loop never ran, because it waits on both queues being non-empty and one of them stayed empty for the whole simulation. So the correct reading is “this check was never exercised”, not “this data disagreed”.

That distinction matters enough that I would change the reporting: a scoreboard should assert at end of test that every queue it owns is both non-empty and fully drained. An empty queue and a leftover queue are different bugs, and both are currently invisible. The verdict logic in report_phase already requires matches > 0, which catches it — but the message should say so.

There is no reference model. How do you know the DUT is right and not just self-consistent?

Largely, I do not — and that is the biggest structural gap in the environment. What exists is three data-conservation checks: bytes read from memory should equal bytes sent as a TLP, bytes received as a completion should equal bytes written into memory, and TX payload should equal RX payload on the loopback. Those catch corruption and loss. They do not catch a wrong header field, a wrong tag, wrong ordering, or a TLP that should never have been sent.

The right structure is a predictor: a class that receives each proc-side AXI transaction and each TLP, models what the Transaction Layer specification says should happen, and produces an expected TLP that the scoreboard compares field by field against the observed one. That also gives you somewhere to encode the ordering rules — posted cannot pass posted, completions cannot pass posted — which no amount of byte comparison will find.

Both monitors watch the same wires the driver drives. What stops a monitor from being wrong in the same way?

On the DLL TX side, nothing structural — dll_tx_responder and dll_tx_mon decode the same stream independently, which is genuine redundancy: they were written separately and disagree in one visible place (the responder captures a DWORD the monitor does not, which is finding B). That disagreement is a feature; it is how the off-by-one surfaced.

On the RX side the risk is real: dll_rx_drv drives what the responder computed, and dll_rx_mon collects it back. If the responder decodes a header field wrong, the driver sends it wrong and the monitor faithfully reports the wrong value, and the loopback compare still passes. The defence would be assertions in the interface that check TLP well-formedness independently of both — header length matching the payload DWORD count, reserved bits zero, completion tag matching an outstanding request. Currently the interface has only X-checks.

Why one clock for both the AXI and DLL domains?

Because the DUT has no clock-domain crossing in it. state_dll runs off tl_dll_clk and state_axi runs off aclk, but they exchange values through plain shared variables with no synchroniser, no handshake and no FIFO. If those two clocks were independent, every one of those exchanges would be a metastability hazard.

Tying both to one 100 MHz clock in top_tb is therefore an honest reflection of what the design supports, not a shortcut. Making them asynchronous is a real piece of work on the DUT first — two-flop synchronisers on the control flags, an async FIFO for cpltlpdataQ — and only then a testbench change. If asked what I would verify after that: CDC assertions, and a test sweeping the clock ratio.

Six of your DUT states have empty bodies. What happens if one is entered?

The FSM stops. S_CFG_WR, S_CFG_RD, S_IO_WR, S_IO_RD, S_MSG and S_ERROR are all reachable from the dispatch state — a CPU writing tlp_transfer_config_reg = IO_WR gets a silent hang, not an error. That is precisely the shape of failure that cost the most debug time during bring-up, twice.

Two things catch it cheaply. First, an SVA watchdog on the interface: state_dll must not remain unchanged for more than N clocks outside the known idle states. Second, a UVM heartbeat or a global timeout that ends the simulation with a clear message instead of letting it spin — during bring-up I was wrapping runs in timeout 120 vsim … and checking for exit code 143 to distinguish a hang from slowness, which works but is outside the testbench. It belongs inside it.

Your coverage is two covergroups. Is that enough?

No, and the two that exist are the right two to have written first: one proves which payload sizes were programmed, one proves which TLP types actually crossed the interface. Those answer “did my test do what I think it did”, which is the first question coverage should answer.

What is missing, in the order I would add it: crosses of TLP type against virtual channel and against payload length; bins on first and last DWORD byte-enables, which is where alignment bugs live; AXI burst length, burst type and response code; and then error scenarios — poisoned TLP, unsupported request, completion timeout, malformed header. Most of that last group needs DUT work before it can be covered, which is a legitimate answer: coverage goals that the design cannot yet reach are a plan, not a score.

What would you do differently if you started this again?

Four things, in order of how much they would have saved.

One: put shared types and state in a package from the start rather than `include-ing a class into two compilation units. That single decision removes bug #9 and its latent twin entirely.

Two: build the predictor before the scoreboard. Byte queues were quick to write and are the reason the failures are hard to attribute — a mismatch tells you nothing about which transaction it came from.

Three: fix the toolchain question first. Two full days of the bug log are UVM 1.2 macros compiled against a 1.1d library. Checking what import uvm_pkg::* actually resolves to is a five-minute check that would have prevented 224 errors and two red herrings.

Four: use uvm_config_db with hierarchical paths instead of uvm_resource_db::read_by_type, so that two interfaces of the same type cannot silently cross-wire.
